Why a graph?

Use a graph when control is part of the product

Model / tool loop

model↔tools

Best when: the model chooses tools until it can answer.

Default: start with LangChain create_agent.

Explicit workflow

plan→fan-out→gate

Best when: order, parallelism, recovery, or review changes correctness.

Use: LangGraph's lower-level runtime.

Inference: choose LangGraph for a runtime guarantee you can name and test—not because the app contains an LLM.

Practice 1 · diagnose

Repair the state contract

Three parallel research tasks each return {"findings": [item]}. The state declares findings: list[Finding] with no reducer.

Predict: what breaks? Then specify a safe merge rule and a deterministic ordering strategy.

Use Annotated[list[Finding], operator.add]. Give each finding a stable topic or rank, then sort after the parallel superstep. The reducer combines values; it does not promise completion order or deduplicate retries.

Routing

Four control primitives, four different jobs

Static edge

Trigger: node completes

Job: invariant order

add_edge(A, B)

Conditional edge

Trigger: route function

Job: branch or loop

separate work from routing

Send

Returns: task + input

Job: dynamic map

one topic → one worker

Command

Returns: update + goto

Job: atomic decision

review → revise / finish

Use Command when state change and next hop are one decision; otherwise a conditional edge keeps topology more visible.

Verified Python · state

Define state for the run you need to recover

import operator
from typing import Annotated
from typing_extensions import TypedDict

class Finding(TypedDict):
    topic: str
    claim: str
    source_url: str

class ResearchState(TypedDict, total=False):
    brief: str
    topics: list[str]
    findings: Annotated[list[Finding], operator.add]
    ideas: list[str]
    review: dict[str, str]
    final_brief: str

class ResearchTask(TypedDict):
    topic: str
verified: langgraph==1.2.11 parallel-safe findings task-specific Send input

Typed shape is not runtime validation. Normalize and validate external model/tool output before state update.

Verified Python · topology

Compile the smallest useful graph

builder = StateGraph(ResearchState)
builder.add_node("plan_research", plan_research)
builder.add_node(
    "research_topic",
    research_topic,
    retry_policy=RetryPolicy(
        max_attempts=3,
        retry_on=ConnectionError,
    ),
)
builder.add_node("synthesize_ideas", synthesize_ideas)
builder.add_node("review_ideas", review_ideas)
builder.add_node("finalize", finalize)
builder.add_edge(START, "plan_research")
builder.add_conditional_edges(
    "plan_research",
    fan_out_research,
    ["research_topic"],
)
builder.add_edge(
    "research_topic", "synthesize_ideas"
)
builder.add_edge("synthesize_ideas", "review_ideas")
# review_ideas routes with Command
builder.add_edge("finalize", END)

graph = builder.compile(
    checkpointer=InMemorySaver()
)
START→plan⇢research × N→synthesize→review→finalize

Verified with langgraph==1.2.11. Search and model nodes use deterministic stand-ins so graph behavior is testable without credentials.

Safe before interrupt

Pure computation, reads, or idempotent upserts.

Unsafe before interrupt

Append-only writes, charges, sends, or non-idempotent creation.

2 · Validate and resume

from langgraph.types import Command

# Application authorizes user + thread,
# then validates the selected idea.
completed = graph.invoke(
    Command(resume={
        "action": "approve",
        "idea": ideas[0],
    }),
    config,
)

print(completed["final_brief"])

A thread ID is not authorization. Treat resume as an authenticated state-changing API call. Verified with langgraph==1.2.11.

Successful parallel task writes can survive a sibling failure.

Not guaranteed

An external side effect is not deduplicated because its state write persisted.

Full checkpoints are superstep snapshots; per-task pending writes support recovery inside the superstep.

Replay

Resume from a historical checkpoint. Nodes before it are reused; nodes after it execute again.

Fork

Create a new checkpoint with modified state, then compare the alternative trajectory.

Downstream model and API calls can differ. Record model, prompt, tool, and data versions when comparison matters.

Failure design

Classify failures by who can resolve them

Retry

Owner: infrastructure

503, connection reset, temporary quota.

RetryPolicy

Loop

Owner: model/workflow

Unsupported claim, malformed structured output.

state + route

Interrupt

Owner: user/reviewer

Ambiguous scope, permission, consequential choice.

interrupt()

Surface

Owner: engineering

Invariant violation, schema bug, impossible state.

exception + alert

Catching everything and asking the model to recover converts defects into expensive, opaque loops.

Practice 4 · choose

Route each failure to its resolver

A. Search returns HTTP 503.

B. Synthesis emits an unsupported claim.

C. The brief omits the target user.

D. Normalized state violates an invariant.

Choose: retry, loop, interrupt, or surface. Name the owner and the failure signal.

A retry transient infrastructure · B loop with evidence gaps · C interrupt for user input · D surface as an engineering defect.

In the 1.2 docs, node timeouts and node-level error handlers are alpha. Retry policies are sufficient for the verified example.

Recap

A reusable LangGraph design review

What outcome and terminal states exist?
What facts must survive a retry or pause?
Which keys overwrite, reduce, or need stable order?
Where are the retry, approval, and effect boundaries?
Which routes are static, conditional, Send, or Command?
What repeats after failure, replay, or interrupt?
Which data is thread state, store memory, or source truth?
How are loops, concurrency, time, and cost bounded?
Which exact tests and quality metrics prove behavior?
Why is this not simpler as Python or create_agent?

If those answers are explicit, the graph is explainable. If they are testable, it is on the path to production.
